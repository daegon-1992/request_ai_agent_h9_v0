# h7_v0 현행 유동해석 의뢰 기준

## 1. 문서 목적

이 문서는 구조해석 담당자 정보요청 양식과 동일한 관점으로 현재 h7_v0 유동해석 의뢰 기능을 역정리한 기준 예시다. 구조 담당자는 이 문서를 보고 “현재 유동해석은 어떤 유형, 필드, 객체, Case와 검증 규칙으로 구성되어 있는지” 확인할 수 있다.

내용은 2026-08-20 기준 h7_v0 코드에서 확인한 현행 동작이며 유동해석 업무 담당자의 별도 재승인을 받은 Master는 아니다. 코드에 없는 실제 완료사례, 수행 빈도, 물리적 허용범위 또는 판정 기준은 임의로 만들지 않고 `현행 자료 없음` 또는 `담당자 확인 필요`로 표시한다.

## 2. 현행 사용자 흐름

1. 사업부, 제품군, Platform과 해석유형을 선택한다.
2. Context를 확정하면 해석유형에 맞는 조건 카드가 생성된다.
3. 의뢰자 정보와 프로젝트·개발 정보를 입력한다.
4. Base 제품과 필요한 비교 제품의 총조립 도면번호를 입력한다.
5. 운전, 열교환기 사양, 취출 공기 및 공간 환경 조건을 입력한다.
6. 형상과 활성 조건을 사용자가 Case별로 직접 조합한다.
7. 검증 결과와 미리보기를 확인하고 Word 의뢰서를 생성한다.

## 3. 해석유형 Master

### 현재 선택 가능

| 해석유형 | 사용자 안내 목적 | 활성 조건 카드 |
|---|---|---|
| 풍량 | 제품의 풍량과 유동 분포 검토 | 운전 조건, 열교환기 사양 |
| 기류 패턴 | 온도 조건을 포함한 기류 경로와 공간 분포 검토 | 운전 조건, 열교환기 사양, 취출 공기 조건, 공간 환경 조건 |
| 이슬맺힘 | 결로 위험 위치와 온도·습도 조건 비교 | 운전 조건, 열교환기 사양, 취출 공기 조건, 공간 환경 조건 |
| 열교환기 유속 프로파일 | 열교환기 면의 유속 분포와 균일도 검토 | 운전 조건, 열교환기 사양 |

### 화면에 예정 상태로 표시되어 선택 불가

- 기류도달거리
- PDB
- 실사용 해석
- 집진해석(먼지거동)
- PCB발열
- 다상유동

`일반 유동 해석`과 `열유동 해석`은 기존 저장 의뢰 호환을 위해 조건 규칙에 남아 있지만 신규 선택 항목은 아니다. `냉매누설`은 결과 안내 Master에는 있으나 해석유형 선택 목록에는 없다.

## 4. 공통 Field Rule

### 의뢰 Context

| 필드 | 현행 필수 수준 | 입력 주체 | 규칙 |
|---|---|---|---|
| 사업부 | 필수 | 의뢰자 | Context 확정 전 입력 |
| 제품군 | 필수 | 의뢰자 | 선택 사업부의 제품 분류 사용 |
| Platform | 필수 | 의뢰자 | 선택 제품군의 Platform 사용 |
| 해석유형 | 필수 | 의뢰자 | 현재 활성 4종만 확정 가능 |
| 운전 모드 | 현행 미사용 | 의뢰자/시스템 | 필드는 존재하지만 fieldset 생성 시 빈 값으로 정규화됨 |
| Context 확정 여부 | 시스템 필수 | 시스템 | 확정 후 조건 검증과 다음 단계 진행 가능 |
| 조건 fieldset key/snapshot | 시스템 생성 | 시스템 | 선택 해석유형의 활성 조건 그룹을 고정 저장 |

### 의뢰자 정보

| 필드 | 필수 수준 | 비고 |
|---|---|---|
| 의뢰 번호 | 시스템 생성 | Context 확정 시 미발급이면 생성 |
| 사업부 | 필수 | 초기값 `연구소` |
| 부서 | 필수 | 초기값 `ES CAE팀` |
| 요청자 | 필수 | 현재 코드에 초기 사용자명이 설정되어 있어 일반화 검토 필요 |
| 직급 | 필수 | 현재 코드에 초기 직급이 설정되어 있음 |

### 해석 개요

| 필드 | 필수 수준 | 비고 |
|---|---|---|
| 프로젝트명(PMS) | 필수 | 선택 또는 직접 입력 |
| 개발 등급 | 필수 | A, B, Ca, Cb, Cc, 선행, 미정, 직접 입력 |
| NPI 단계 | 필수 | CP, DV, PV, MP, 미정, 직접 입력 |
| 모델명(Model Suffix) | 필수 | 미정 또는 직접 입력 가능 |
| 의뢰 요청일 | 필수 | 시스템이 오늘 날짜로 초기화 |
| 희망 완료일 | 필수 | 요청일보다 이른 날짜는 허용하지 않음 |
| 해석을 요청하게 된 배경 | 필수 | 진행률 추적 대상 서술 필드 |
| 결과 활용 목적 | 선택 | 현재 public spec상 선택 필드 |
| 해석으로 확인하고 싶은 내용 | 필수 | 진행률 추적 대상 서술 필드 |

## 5. 제품/형상 객체

| 객체·필드 | 현행 규칙 |
|---|---|
| Base 제품 | 정확히 한 개 유지 |
| 비교 제품 | 0개 이상 반복 추가 가능 |
| 도면번호(NPDM MCAD) | 모든 제품에 필수, 영문·숫자·하이픈만 허용, 제품 간 중복 금지 |
| 설명 | Base는 `Base`로 취급, 비교 제품은 Base 대비 형상·조립 상태 차이 필수 |
| geometry_id | 시스템 생성·유지 |
| 형상 축 | 유효한 도면번호가 있는 각 완제품을 `형상 1`, `형상 2` 순서로 생성 |

현행 모델은 총조립 형상 기준이며 부품별 재질, 연결, 하중 적용 면 같은 구조해석 객체는 포함하지 않는다.

## 6. 해석조건 객체와 활성 규칙

### 조건 카드

| 카드 | 필드 | 단위·규칙 |
|---|---|---|
| 운전 조건 | 운전명 | 시스템 생성: `운전 1`, `운전 2` 등 |
| 운전 조건 | 팬 개수 | 기본 1개, 1~4 선택 및 직접 입력 가능 |
| 운전 조건 | 팬 위치 | 여러 팬을 구분하기 위한 설명값 |
| 운전 조건 | 팬 회전수 | RPM, 활성 팬마다 필수 |
| 열교환기 사양 | 사양명 | 시스템 생성: `사양 1`, `사양 2` 등 |
| 열교환기 사양 | 열교환기 유형 | Fin&Tube 또는 Micro-Channel |
| 열교환기 사양 | 관 직경(Pi) | mm, W 접두값이면 Micro-Channel로 분류 |
| 열교환기 사양 | Fin type | Micro-Channel이면 Flat으로 정규화 |
| 열교환기 사양 | 열 수 | 값의 물리 범위는 현행 코드에 없음 |
| 열교환기 사양 | FPI | 값의 물리 범위는 현행 코드에 없음 |
| 취출 공기 조건 | 취출 온도 | °C |
| 취출 공기 조건 | 취출 상대습도 | % |
| 공간 환경 조건 | 공간 온도 | °C |
| 공간 환경 조건 | 공간 상대습도 | % |

각 활성 카드는 반복 추가할 수 있고 첫 번째 카드는 기본 카드로 유지된다.

### 해석유형별 활성 필드

| 해석유형 | 팬 RPM | 열교환기 사양 | 취출 온도 | 취출 RH | 공간 온도 | 공간 RH |
|---|---:|---:|---:|---:|---:|---:|
| 풍량 | 필수 | 필수 | 비활성 | 비활성 | 비활성 | 비활성 |
| 열교환기 유속 프로파일 | 필수 | 필수 | 비활성 | 비활성 | 비활성 | 비활성 |
| 기류 패턴 | 필수 | 필수 | 필수 | 비활성 | 필수 | 비활성 |
| 이슬맺힘 | 필수 | 필수 | 필수 | 필수 | 필수 | 필수 |

기류 패턴의 취출 온도와 공간 온도는 직접 입력하거나 `없음`을 선택할 수 있다. 이슬맺힘은 온·습도 조건을 모두 받는다.

## 7. Case Matrix 규칙

Case Matrix는 가능한 모든 조합을 자동 생성하지 않는 수동 매핑 방식이다.

| 해석유형 | Case 선택 열 |
|---|---|
| 풍량 | 형상, 운전, 사양 |
| 열교환기 유속 프로파일 | 형상, 운전, 사양 |
| 기류 패턴 | 형상, 운전, 사양, 공간 온도, 취출 온도 |
| 이슬맺힘 | 형상, 운전, 사양, 공간 온도, 공간 상대습도, 취출 온도, 취출 상대습도 |

현행 규칙은 다음과 같다.

- 새 유효 형상이 추가되면 형상당 기본 Case 행 한 개를 생성한다.
- 기본 Case에는 각 활성 조건의 첫 번째 입력값을 우선 연결한다.
- 사용자가 행을 추가·삭제하고 각 형상·조건을 직접 선택한다.
- 최소 한 개 Case를 유지한다.
- 같은 형상과 모든 활성 조건값이 동일한 Case는 중복으로 판정한다.
- 삭제되거나 변경되어 더 이상 존재하지 않는 형상·조건 선택값은 비운다.
- 입력한 형상·조건 중 어느 Case에도 사용되지 않은 항목은 Coverage 미완료로 표시한다.
- Word 생성 시 Case 누락, 중복 또는 Coverage 미완료를 허용하지 않는다.

## 8. 검증과 예외 처리

### 제출 차단 검증

- 필수 의뢰자 정보와 해석 개요 누락
- Context 미확정 또는 지원하지 않는 해석유형
- Base 형상 없음, 도면번호 누락·형식 오류·중복
- 비교 형상의 Base 대비 차이 설명 누락
- 활성 조건값 누락
- Case 없음 또는 Case의 형상·활성 조건 선택 누락
- 동일한 Case 조합 중복
- Word 생성 시 사용되지 않은 형상·조건 존재

### 현행 상태값

일반 필드는 `provided`, `missing`, `unknown`, `none`, `skipped` 상태를 가진다. 다만 조건 카드의 일부 UI는 입력 문자열을 직접 `provided/missing`으로 정규화하므로, 필드별 `모름/해당 없음` 허용과 후속 질문 정책이 하나의 업무 Master로 완전히 정리되어 있지는 않다.

## 9. 현행 Gap과 구조해석 확장 시 참고사항

1. 실제 완료 의뢰·보고서 사례는 코드 저장소에 포함되어 있지 않아 현행 규칙의 업무 승인 근거를 확인할 수 없다.
2. `material_type`, 압력, 설치 환경, 결과 확인 항목 등 조건 정의가 남아 있으나 현재 활성 조건 카드에서는 사용되지 않는다.
3. 예정 해석유형 6종은 사용자 안내는 있으나 유형별 Field Rule과 Case 규칙이 없다.
4. 결과 활용 목적은 public spec상 선택이며 현재 최종 미리보기의 핵심 요청 내용에는 직접 표시되지 않는다.
5. 팬 RPM·온도·습도·열교환기 수치의 물리적 허용범위와 단위 변환 규칙이 없다.
6. 여러 팬 사용 시 위치는 미리보기 완전성에 활용되지만 핵심 조건 validator의 필수 판정에는 포함되지 않는다.
7. 조건별 `모름`, `해당 없음`, 담당자 이관과 Agent 추정·확인 정책이 통합 Master로 관리되지 않는다.
8. Case는 형상과 조건값의 선택 조합이며 하중 조합계수나 물리적 상호 배제 규칙은 없다.
9. 사용자 초기값에 특정 요청자·부서 정보가 포함되어 있어 다사용자 운영 시 별도 일반화가 필요하다.

## 10. 코드 근거

- `request_ai_agent_h7_v0/constants.py`: 공통 필드와 해석유형 목록
- `request_ai_agent_h7_v0/condition_fieldsets.py`: 해석유형별 조건 카드·필드 및 Case 열
- `request_ai_agent_h7_v0/state.py`: Context, 제품/형상, 조건 카드와 수동 Case 정규화
- `request_ai_agent_h7_v0/validator.py`: 필수 필드, 형상, 조건과 Case 검증
- `request_ai_agent_h7_v0/request_context_confirmation.py`: Context 확정과 지원 유형 검증
- `request_ai_agent_h7_v0/analysis_type_master.py`: 해석유형별 사용자 결과 안내
- `request_ai_agent_h7_v0/ui.py`: 실제 입력·미리보기·Case·Word 생성 동작
