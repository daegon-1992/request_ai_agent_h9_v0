# h5_v0 워크플로 오케스트레이터 전체 계획

## 1. 전체 목표

기존 h5_v0 폼 UI와 API를 유지하면서 자연어로 CAE 해석 의뢰서 작성을 안내하는 워크플로 오케스트레이터를 점진적으로 추가한다.

최초 사용자 사용 가능 MVP는 다음 흐름이다.

```text
자연어 의뢰 시작
→ 기본 선택값 후보 추출
→ Proposal
→ 사용자 승인
→ Request version 확인
→ Request State 반영
→ 기존 동적 Fieldset 재계산
→ 해석 개요 질문
→ 답변 후보 추출
→ Proposal
→ 승인
→ 공식 Request 재조회와 폼 동기화
→ 다음 질문
```

## 2. 절대 설계 원칙

### LLM이 할 수 없는 일

- 사용자가 제공하지 않은 값 또는 수치 생성
- 임의 온도, 습도, RPM 등 입력
- Request State 직접 변경
- 조건부 필드 활성화 또는 필수 여부 결정
- Case Matrix 계산
- Validation 결과 생성
- Preview 또는 Word 생성 로직 대체

### LLM이 할 수 있는 일

- 사용자 의도 분류
- 자연어에서 값 후보 추출
- 모호성 감지
- 규칙 엔진이 선택한 필드의 질문 문장 생성
- Proposal 변경 내용 요약
- 기존 Validation 결과 설명
- RAG 검색 결과를 근거와 함께 설명

### 모든 Agent 변경 절차

```text
사용자 답변
→ 값 후보 추출
→ Schema 및 Validator 검증
→ Proposal 생성
→ 사용자 승인
→ Request version 확인
→ 승인된 Patch 원자 적용
→ 기존 조건부 Fieldset 재계산
→ 다음 질문 계산
```

승인 전에는 Request State를 수정하지 않는다.

## 3. State 분리

### Request State

의뢰서에 실제 반영되는 공식 데이터이며 단일 진실 원천이다.

### Conversation State

대화 진행 상태만 저장한다. Request 전체 복사본을 저장하지 않으며 `request_id`로 연결한다. 오케스트레이터는 매 처리 시 최신 Request를 다시 조회한다.

## 4. 공통 Field Registry

기존 폼과 오케스트레이터는 동일한 필드 의미와 기존 동적 Fieldset 계산 결과를 사용한다. 신규 Registry는 기존 정의를 복제하기보다 Adapter로 제공하는 것을 우선한다.

필수 정보:

- field_id와 State 저장 경로
- 표시 이름, 섹션, 입력 타입, 단위
- 필수 여부와 조건부 필수 규칙
- 표시 조건과 의존 필드
- 검증 metadata
- 질문 우선순위와 질문 설명

## 5. Next Field Planner

다음 필드는 규칙 기반 Planner가 선택한다.

- 현재 활성화된 필드만 대상
- 미입력 필드 대상
- 필수 필드 우선
- 다른 필드를 활성화하는 상위 필드 우선
- Validation을 막는 필드 우선
- 현재 Workflow 단계 우선
- 사용자 답변이 쉬운 필드 우선
- 한 번에 최대 1~2개의 연관 필드

LLM은 선택된 필드를 자연스러운 질문으로 표현하는 역할만 담당한다.

## 6. 작업 분할 전략

- 001~004: 읽기 전용 구조 조사
- 005: 실제 구조 기반 최소 변경 설계
- 006~009: Field Registry, Request version, Proposal 안전 기반
- 010~017: Conversation, Workflow, Planner, Tool, Router, 백엔드 수직 흐름

- 031~032: 핵심 회귀와 제한적 안정화

## 7. MVP 완료 지점

- 사용자 사용 가능 MVP: `H5-ORCH-020`

## 8. 계획 갱신 원칙

- 현재 계획은 기준안이며 고정 계획이 아니다.
- 각 단계 후 Worker와 별도의 Reviewer가 결과를 검토한다.
- 완료된 단계는 이유 없이 재실행하지 않는다.
- 실제 구조가 최초 가정과 다르면 실제 구조를 우선한다.
- 신규 선행 단계는 `017A` 같은 보조 ID로 삽입한다.
- 불필요한 단계는 축소·삭제할 수 있다.
- 커진 단계는 하위 단계로 분리한다.
- 계획 변경 이유를 Roadmap에 기록한다.
- 다음 실행 프롬프트는 최신 인수인계 문서를 기준으로 다시 생성한다.

## 9. 공통 검증 원칙

기본 우선순위:

1. 변경 파일 문법 및 인코딩 검사
2. 변경 기능 직접 단위 테스트
3. 핵심 API/UI 경로 제한적 Smoke Test
4. 영향 가능성이 높은 기존 테스트 일부

전체 Suite, 모든 제품군 조합, 광범위한 시각 회귀, 실제 LLM 품질 평가는 해당 단계에서 반드시 필요할 때만 수행한다.

State 손상, 승인 우회, stale Proposal, 중복 승인, 조건부 필드 유실 위험은 반드시 직접 검증한다.

- 목표와 실제 수행 내용

- 중요 설계 결정

- 최소 검증과 실패한 검증
- 알려진 문제와 위험
- 다음 단계 참고사항
- 다음 단계 예상 수정 파일
